# Решения по реализации

Здесь записаны решения в местах, где ТЗ допускает трактовку, и честные ограничения. Принцип выбора: самый простой вариант, который не ломает офлайн-режим.

## Инфраструктура

| # | Решение | Почему |
|---|---|---|
| 1 | Проект лежит в корне репозитория, а не в подпапке `dolcepharm-lms/` | Репозиторий и есть проект. Структура внутри повторяет раздел 4 ТЗ |
| 2 | Вместо отдельного сервиса `frontend-build` с общим volume фронтенд собирается multi-stage внутри образа nginx (`nginx/Dockerfile`) | Одна команда `docker compose up --build`, нет гонки «nginx стартовал раньше, чем собрался dist» |
| 3 | Если сертификатов mkcert нет, nginx при старте сам создаёт самоподписанный (`nginx/ensure-certs.sh`) | `docker compose up` работает сразу. Для телефона рекомендуем mkcert, потому что SW, камера и WebCrypto требуют доверенного HTTPS |
| 4 | Таблицы создаются через `create_all` при старте, сид запускается перед uvicorn, если в БД нет пользователей | Так требует ТЗ. Миграции (Alembic) для MVP не нужны |
| 5 | Перечисления (`role`, `status`, `type`…) хранятся как `VARCHAR`, значения проверяет Pydantic | Не нужны миграции PG-enum при добавлении значения |
| 6 | Роутеры `departments` и `devices` объединены с `users`/`auth`, а `materials`, `categories` и `certificates` — с `courses`, `files` и `reports` | Меньше файлов, пути API те же, что в разделе 9 |
| 7 | Фоновые задачи: FastAPI `BackgroundTasks`. LibreOffice защищён блокировкой (один процесс за раз) | Параллельный запуск `soffice` с одним профилем падает |

## Данные и синхронизация

| # | Решение | Почему |
|---|---|---|
| 8 | **Устройство регистрируется на пару «пользователь + браузер»**: в Dexie `device` ключ — `userId` | ТЗ требует, чтобы `device_id` принадлежал пользователю токена, и разрешает смену пользователя на одном телефоне. Так у каждого свой HMAC-секрет, а QR-пакет всегда принадлежит владельцу устройства |
| 9 | `syncEngine` отправляет только записи текущего пользователя. Записи другого пользователя ждут его входа или уходят через QR | Нельзя отправлять чужие данные со своим JWT |
| 10 | Добавлена таблица `sync_logs`: каждая пачка `/sync` и `/sync/qr` с `online_since` (когда телефон увидел сеть, пересчитано на часы сервера) и `lag_ms` | Отчёт «Синхронизация» должен доказывать требование «≤ 1 минута после появления сети». Разность `synced_at − ended_at` для событий, созданных офлайн, показывает время без сети, а не задержку синхронизации |
| 11 | `/sync/state` возвращает состояние целиком, `since` принимается, но не фильтрует | Состояние сотрудника — десятки строк, дифф не окупается |
| 12 | Признак `created_online` в payload: если запись создана при живой сети, `source='online'`, иначе `'sync'` | Отчёт различает «сдал онлайн» и «сдал офлайн, потом синхронизировал». Отдельный `POST /attempts` тоже есть |
| 13 | `session_end` не пишется на каждом `pagehide`: на `pagehide` сохраняется только состояние трекера. Если вкладку убили, при следующем запуске незакрытая сессия закрывается по времени последней активности. После 30 минут бездействия начинается новая сессия | На мобильных `pagehide` срабатывает и при обычном переключении приложений, и при перезагрузке страницы. Иначе в отчёте было бы много коротких ложных сессий |
| 14 | В отчёте «Сессии» вход и выход сопоставляются по `(user, device, started_at_client)`: `session_end` несёт время начала своей сессии | В схеме `activity_events` нет `session_id` |
| 15 | Компакция QR: склеиваются подряд идущие `material_interval` одного материала с разрывом ≤ 5 с (это чекпойнты одного просмотра) | В событиях нет `session_id`. Разрыв ≤ 5 с означает тот же непрерывный просмотр |
| 16 | Известный крайний случай компакции: если часть интервалов уже дошла по сети, но телефон не получил ответ, а потом те же интервалы склеены в QR-пакет, и первый id уже на сервере, весь склеенный интервал считается дублем | Сценарий требует обрыва сети ровно в момент ответа сервера. Потеря — максимум несколько минут учёта одного материала |
| 17 | Смещение часов для QR берётся из `client_now` пакета, только если устройство ещё ни разу не синхронизировалось по сети (`devices.offset_known`). Иначе используется сохранённое смещение | Так требует ТЗ: время создания пакета ≠ времени приёма |

## Тесты и оценивание

| # | Решение | Почему |
|---|---|---|
| 18 | Пустой открытый ответ получает 0 баллов и **не** уходит на проверку | Проверять нечего. Логика одинакова в `grading.py` и `grading.ts` |
| 19 | Ключевое слово — одно слово. Если ввели фразу, берётся первое слово. Основа слова: первые `max(4, len−2)` символа | Простая замена стемминга по ТЗ. Клиент проверяет офлайн, перебирая префиксы слов ответа, — это эквивалентно `startswith` на сервере |
| 20 | Порог `keywords_min` ограничен числом ключевых слов | Иначе вопрос нельзя было бы засчитать автоматически |
| 21 | Округление `score` — «половина вверх» (`floor(x*10+0.5)/10`) на обеих сторонах | `round()` в Python банковский, `Math.round` — нет. Нужна полная идентичность |
| 22 | При `PUT /courses/{id}/test` id вопросов и вариантов сохраняются, если их передали | Попытки, начатые офлайн на старой версии, по-прежнему сопоставляются с вопросами |
| 23 | Варианты `order` в пакете перемешаны сервером; правильный порядок есть только в `position_hashes` | Иначе порядок в IndexedDB и был бы ответом |
| 24 | Пояснения (`explanation`) входят в пакет открытым текстом | Они нужны для разбора офлайн после сдачи. Это не варианты ответа |
| 25 | Первая публикация курса не меняет `version` (1). Каждая следующая делает `version++` и пересоздаёт соль | Версия означает «что-то изменилось после публикации» |

**Честно о защите ответов (раздел 8.2).** Хэши `sha256(salt:…)` не защищают от решительного взломщика: вариантов мало, а соль лежит в пакете, поэтому перебор тривиален (для `multi` клиент вообще вычисляет правильность каждой опции). Хэши решают одну задачу — правильный ответ нельзя просто подсмотреть в IndexedDB. Итоговую оценку **всегда** пересчитывает сервер по своим данным, и в отчётах, сертификатах и протоколах используется только серверная оценка.

## Фронтенд

| # | Решение | Почему |
|---|---|---|
| 26 | i18n с «естественными» ключами: ключ — русская строка, `kk.json` — переводы. Непереведённые строки показываются по-русски | Быстро писать интерфейс и не держать сотни искусственных ключей. Экраны оператора переведены на казахский полностью, кабинеты методиста — частично |
| 27 | Markdown рендерится собственным небольшим парсером в React-элементы, HTML из текста не вставляется никогда | Безопасность без внешних зависимостей |
| 28 | pdf.js — legacy-сборка `pdfjs-dist@4.10` | Поддержка iOS 16.4 (в современной сборке нужен `Promise.withResolvers`) |
| 29 | Файлы курсов хранятся в IndexedDB как Blob и открываются через `URL.createObjectURL`. Service Worker кэширует только оболочку | Как рекомендует ТЗ: надёжнее на iOS Safari |
| 30 | Отдельная таблица Dexie `progress` (секунды и «открыт» по материалу) | Прогресс и «тест открыт после изучения» нужны мгновенно и офлайн, без пересчёта outbox |
| 31 | Длительность теста считается по `performance.now()`, если страница не перезагружалась (`startedPage`), иначе — по настенным часам | Монотонные часы сбрасываются при перезагрузке |

## Известные ограничения

- **iOS Safari:** нет Background Sync, поэтому синхронизация идёт только при открытом приложении. Квота хранилища меньше, и ОС может очистить данные, если PWA не установлено на экран «Домой». Камера в установленной PWA работает с iOS 16.4.
- **LibreOffice** конвертирует сложные PPTX с анимацией упрощённо — это статичный PDF.
- **Права на файлы:** `GET /files/{id}` доступен любому авторизованному пользователю. Сотрудник видит только назначенные курсы и пакеты, но прямую ссылку на файл не проверяем: в MVP все материалы внутренние.
